## Wallabag deployment to production K3s homelab

### What was attempted

Deploy a self-hosted [[Wallabag]] (read-it-later) instance into the
[[Ninjatronics K3s Homelab]] with PostgreSQL, Traefik ingress, cert-manager
TLS, Cloudflare Tunnel exposure, OpenBao/ESO secrets, and persistent storage
— all fully GitOps-managed through Flux.

### Research and image verification

- Researched official Wallabag Docker documentation (hub.docker.com,
  github.com/wallabag/docker).
- Pulled `wallabag/wallabag:2.6.14` and inspected the image directly:
  - Exposed port: 80/tcp (nginx + php-fpm via s6-svscan)
  - Runs as root by design (s6-svscan + nginx port-80 binding)
  - Entry point: `/entrypoint.sh` with CMD `wallabag`
  - PHP 8.1.32, nginx, Alpine 3.24 base
  - Digest: `sha256:4a527e027e0d59e87c14225ef11e005af3d4890374202ad319ce5e63dfc66709`
- Confirmed `/api/info` returns JSON with 200 status for health probes.

### Architecture decision: dedicated PostgreSQL

No shared PostgreSQL infrastructure exists in the homelab. Every app that
needs PostgreSQL (Forgejo, Firecrawl) brings its own dedicated Deployment.
Followed the same pattern: standalone PostgreSQL 17.11-alpine Deployment in
the Wallabag base, pinned to niner, with `pg_isready` probes.

Redis excluded (optional for async import workers). SMTP excluded (no mail
server).

`flux diff kustomization apps` accepted by the API server.

### PostgreSQL 15+ schema privilege issue

**Problem:** The initial deploy failed with `SQLSTATE[42501]: Insufficient
privilege: 7 ERROR: permission denied for schema public` during
`wallabag:install`. PostgreSQL 15+ revoked `CREATE` on the `public` schema
from non-superusers. The Wallabag entrypoint creates the `wallabag` database
and user, then runs `wallabag:install` which connects as the `wallabag`
user (non-superuser) and needs `CREATE` on `public` to create the
`migration_versions` table.

**Fix:** Set `POSTGRES_USER=wallabag` so the PostgreSQL superuser IS the
Wallabag app user. Set `POSTGRES_DB=postgres` (not `wallabag`) so the
Wallabag entrypoint sees the `wallabag` database does not yet exist, creates
it, and runs `wallabag:install` as the superuser. Also set
`PGDATABASE=postgres` so the entrypoint's `psql` calls connect to the
`postgres` maintenance database by default (without this, psql defaults to
the `wallabag` database which does not exist at first boot, causing
`FATAL: database "wallabag" does not exist`).

Both `POSTGRES_PASSWORD` and `SYMFONY__ENV__DATABASE_PASSWORD` use the same
OpenBao property (`database-password`) because they authenticate the same
PostgreSQL role.

### What worked

- `wallabag:install` ran successfully on first boot with the corrected

  setup", "Config successfully setup".

- TLS certificate issued by cert-manager (`letsencrypt-production-cloudflare`).
- Cloudflared pod auto-rolled via Kustomize configMapGenerator hash when

- `curl -I https://wallabag.ninjatronics.io` returns HTTP/2 302 → /login.
- `curl -s https://wallabag.ninjatronics.io/api/info` returns 200 with

### Decisions made

## Calibre deployment to production K3s homelab

### What was attempted

Deploy a self-hosted [[Calibre]] content server into the
[[Ninjatronics K3s Homelab]] with a custom non-root container image
published to GHCR, Traefik ingress, cert-manager TLS, Cloudflare Tunnel
exposure, OpenBao/ESO secrets, and persistent local-path storage — all
fully GitOps-managed through Flux.

### What happened

- Built a custom Calibre image from `containers/calibre/Dockerfile`:
  two-stage build on `debian:trixie-slim`, downloads official Calibre 9.14.0
  tarball, verifies SHA-256, strips GUI components (Qt Wayland/X11 platform
  plugins, ebook viewers, editors, SMTP), runs as non-root UID/GID 10001
  with `QT_QPA_PLATFORM=offscreen`.
- Entrypoint initializes the library if empty, creates/updates the user in
  `users.sqlite`, unsets credential env vars, then execs `calibre-server`
  on port 8080 with `--enable-auth`.
- Published the image to GHCR at `ghcr.io/gmakezig/calibre-server:9.14.0`
  with digest pinning.
- Created Kubernetes manifests: namespace, base (deployment, configmap,
  service, PVCs, secret.example), production overlay (ingress,
  ExternalSecret), and cloudflared tunnel route.
- Flux reconciled all Kustomizations to `main@sha1:be0edee`.
- TLS certificate issued by cert-manager (`letsencrypt-production-cloudflare`).
- Cloudflare DNS CNAME and tunnel route configured for
  `calibre.ninjatronics.io`.

### What worked

- Custom non-root container image built and published to GHCR.
- `kubectl kustomize` at all affected layers succeeded.
- Flux reconciled all Kustomizations Ready=True.
- ExternalSecret synced from OpenBao (`secret/apps/calibre`).
- Both PVCs Bound on niner (local-path, WaitForFirstConsumer).
- TLS certificate Ready=True (DNS-01 via Cloudflare).
- Public web UI: HTTP 200.
- `/opps` unauthenticated: HTTP 401 (auth enforced).
- Invalid credentials rejected.
- Sentinel Phase 2: PASS WITH NOTES.

### GHCR image owner correction

The initial Makefile and repo runbook referenced `ghcr.io/ninjatronics/`
as the image owner. The correct GHCR owner is `GMakeziG`. This was
corrected in commit `f5d810a` before the production deployment was
finalized. The repo's `docs/calibre-runbook.md` still contains the old
owner and the outdated `calibre.internal` hostname — the vault
[[Calibre]] and [[Calibre Operations]] notes are the current source of
truth.

### GHCR publishing requirements

- A **classic** Personal Access Token with `write:packages` scope is
  required to push to GHCR. Fine-grained PATs may not work.
- The GHCR package was set to **public** visibility, which permits
  anonymous Kubernetes image pulls without image pull secrets.
- The deployment image is digest-pinned:
  `ghcr.io/gmakezig/calibre-server:9.14.0@sha256:429bb9...39013d`.

- Custom Docker image rather than using an upstream image — the official

### Lessons learned — Nova orchestration model

- **Nova is orchestration-only.** Nova formulates bounded assignments,
  invokes the approved dispatcher, waits for completion without repeatedly
  polling, reads only `result.md`, evaluates, and presents decisions. Nova
  does not perform specialist implementation work directly.
- **Specialist execution must use `dispatch-codex.sh` -> Herdr -> Codex
  interactive.** This is the approved execution path. The bounded result
  returns through `result.md` handoffs only.
- **Never use direct `codex exec` as an unauthorized fallback.** If the
  approved dispatch path fails (blocked, sandbox, auth), stop and report
  to Gerso — do not construct alternate commands or bypass Herdr.
- **Never escalate to `danger-full-access` without explicit approval.**
  Sandbox escalation is an operational approval gate, not a
  troubleshooting step.
- **Blocked Herdr panes must remain open for human approval.**
  `dispatch-codex.sh` preserves the pane on blocked status and exits
  non-zero. Do not close, retry, or re-run the dispatcher on a blocked
  pane — report the pane ID and label to Gerso and leave it open.
- **Specialist results return through bounded `result.md` handoffs only.**
  Nova reads `result.md` from the handoff directory — not from the
  specialist's live transcript or terminal output.
- **Specialist Codex dispatches use `--disable plugins` to reduce
  context.** This keeps the specialist's context window focused on the
  assignment.
- **Correct GHCR owner is `GMakeziG`, not `ninjatronics`.** Custom images
  therefore use `ghcr.io/gmakezig/...`.
- **GHCR publishing required a classic PAT with `write:packages`.**
  Fine-grained PATs may not work for GHCR.
- **Public GHCR visibility permits anonymous Kubernetes image pulls.**
  No image pull secret is needed when the package is public.
